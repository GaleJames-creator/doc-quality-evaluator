# Changelog

## August 2026

### Added

* **Batch evaluation.** `evaluate_batch.py` scores many files in one run, taking any mix of files and folders anywhere on disk&mdash;no `DOC_PATHS` restriction and no git involvement. It prints an aligned score table, optionally writes the Markdown report (`--report`), and exits non-zero when any file falls below `--threshold` (default `3`), so it gates scripts the way the CI check gates pull requests. See [Batch evaluation](docs/batch-evaluation.md).
    * `--dry-run` lists every file and its disposition without calling the API, added after a first run against a real documentation repository scored roughly one hundred vendored package READMEs before anyone could see what it had picked up.
    * Folder recursion skips `node_modules` and dot-directories; `--all` restores the previous behavior.
    * `--exclude GLOB` and a `.docqualityignore` file exclude files from outside the document. This matters because `skip-evaluation` frontmatter renders as a visible table on GitHub, so a repository README carrying the flag showed a stray `skip-evaluation | true` row above its title. Explicitly named files override any pattern.

* **OpenAPI YAML support.** `.yaml` and `.yml` files are parsed with PyYAML and evaluated as `docType: reference`. The prompt grades the human-readable content&mdash;`summary`, `description`, parameter and response documentation, examples&mdash;and does not penalize Structure for the spec-mandated layout. Non-spec YAML found by folder recursion is skipped as "not an OpenAPI spec" rather than failing the gate, since documentation repositories routinely contain linter rulesets and CI workflows; an explicitly named non-spec file still errors. Added `samples/books-api.yaml` as a working example.

* **Proofreading workflow.** `.github/workflows/docs-lint.yml` runs codespell and `tools/check_docs.py` on any pull request touching Markdown. Neither needs an API key and both finish in seconds. Added after two typos reached the published documentation and were found by a human reader; testing showed codespell catches neither, because every word in `The The` and `his applies` is spelled correctly. `check_docs.py` covers repeated words, sentences missing a leading capital, broken relative links, anchors pointing at renamed headings, and raw dashes where house style wants an entity.

* **Link checking in CI.** `markdown-link-check` runs on every push to `main` and every pull request, configured at `.github/mlc_config.json`, which the style guide names as the standard rather than the local fallback. It runs as a separate job from the prose checks so a broken link and a typo are distinguishable at a glance. The file set matches `tools/check_docs.py`: evaluation inputs under `samples/` and verbatim evaluator output are excluded, since their links resolve in the repositories they came from rather than this one. Two hosts that refuse automated requests are suppressed, each verified reachable by hand first.

* **Saved report samples.** `report_samples/` holds unedited output from a real CI run and a real batch run, so readers can see the report format without cloning the repository or spending API credits. The working reports stay out of version control.

* **Pipeline diagrams.** Batch and continuous integration diagrams, generated by `make_diagrams.py` from layout data rather than drawn by hand, so a pipeline change is a code edit and a rerun.

### Changed

* **Split the README into a short overview plus a `docs/` folder**, and moved this changelog to a top-level `CHANGELOG.md`. The README had grown to 871 lines covering overview, setup, continuous integration, batch evaluation, customization, feedback interpretation, troubleshooting, and release history&mdash;five Diátaxis types in one document, which is the structural problem the evaluator itself flags most often. No prose was lost in the move; only the file tree was dropped, replaced by a shorter "What's here" table.

* **Rewrote Setup around the batch runner** after a new-reader review found it teaching a workflow the tool had outgrown: copy each file into `samples/`, run a single-file evaluator, repeat for every additional file. Added a "Which tool should I use?" table, since four entry points existed with no guidance and the weakest one was described first.

* **Extracted shared report rendering into `report.py`.** The console table and Markdown renderers lived inside the CI runner; both runners now import them from one module, with the threshold passed as a parameter, so the two cannot drift apart.

* **Listed skipped and gate-failing files one per line** in both the console output and the Markdown report, each with its reason. With 19 skipped files and absolute paths, the comma-joined form was unreadable, and the gate-failure list is the block a reader acts on.

* **Expanded the guidance on reading evaluator output.** See [Interpreting evaluator feedback](docs/interpreting-feedback.md) and [Batch evaluation](docs/batch-evaluation.md).
    * Recorded what the evaluator reliably catches, using two confirmed findings from a threshold-4 run: a `language` field specified as ISO 639-1 while every example used the BCP 47 tag `en-US`, and a pagination example requesting `limit: 100` above a response reporting 87 items across 5 pages. The page had documented false positives in detail while recording none of the genuine catches.
    * Added the rule that a flat score of 1 on every criterion means the document is out of scope, not poor quality: the tool schema gives a refusal nowhere to land but the floor.
    * Recorded a run against this repository's own `docs/` folder, including two pages that failed and were left uncorrected, because satisfying the rubric would mean adding endpoints and error codes to documents that describe a tool rather than an API.
    * Set threshold guidance from observed data: keep the CI gate at `3` and use `4` as a periodic polish lens, since documents scoring 4.0 to 4.4 flip between pass and fail across runs with no edits.

* **Added Prerequisites sections to the three how-to pages.** House style requires them and none had one, so each page implied a reader arriving fully set up. Existing readers get a separate upgrade note where a new dependency is documented, since "complete the setup" is the wrong instruction for someone who completed it months ago.

* **Added `PyYAML` and `codespell` to `requirements.txt`.** PyYAML was previously pulled in transitively; codespell had been documented as a command without an install step.

### Fixed

* **Added a stray-period check to `tools/check_docs.py`.** macOS substitutes `. ` for a double space when "Add period with double-space" is enabled, and padding a table cell to align its pipes is exactly a double-space keystroke. The result lands in parameter names and required flags, reads as deliberate, and no spell checker objects because a period is valid text. Five instances had reached published documentation, including a column header rendering as "Type." and a `No.` in a Required column. The check looks only at table cells, flags a single-token cell ending in a period, and allows abbreviations such as `e.g.` and non-ASCII tokens, since a document about encoding problems legitimately shows corrupted text in a before-and-after table.

* **Settled the dash convention and made `tools/check_docs.py` enforce it.** Entities are set closed, as in `word&mdash;word`, with two exceptions the checker now understands. A table cell whose entire content is a dash keeps its padding, because there the dash marks "not applicable" rather than punctuating a sentence. Headings are exempt from both dash rules: a heading's text generates its anchor, other pages link to that anchor, and platforms differ on whether they slug rendered text or raw source, so converting one trades a possible broken cross-reference for a cosmetic gain.

* **Stopped `tools/check_docs.py` reporting repeated numbers as repeated words.** Test card numbers such as `4242 4242 4242 4242`, routing numbers, and phone numbers tripped the doubled-word check throughout a payments tutorial. A doubled word is a typo; a doubled number group is usually the point. Digit-only repeats are now ignored, and doubled words are still caught.

* **Fixed `tools/check_docs.py` resolving relative paths against its own repository instead of the working directory.** Running it from another project with a relative path silently checked a same-named file in this repository and reported it clean&mdash;a false all-clear, which is worse than no check. Found by pointing it at a portfolio README that turned out to have eight violations. Absolute paths were always correct; relative paths now resolve from the working directory, with a fallback so invocations from inside this repository keep working.

* **Taught the CI runner to see YAML.** `ci/evaluate_changed.py` still matched `.md` and `.mdx` only, so a changed OpenAPI specification was never scored on a pull request even though the batch runner scored it and the documentation claimed both did. Found while opening the first pull request after adding YAML support: the gate would have passed by finding nothing to evaluate. A YAML discovered from a diff that isn't a specification is skipped with a reason rather than failing the check, matching the batch runner.

* **Corrected the Python requirement from "Python 3.x" to 3.10 or later.** The batch runner, report renderer, and CI runner use `X | None` annotations that raise a `TypeError` at import on 3.9. Added a troubleshooting entry for that error.

* **Corrected the claim that `build_index.py` is needed for `RAG-enhanced` evaluation only.** The batch and CI runners require the index too; only the `baseline` evaluator runs without it. The setup step and the `Collection 'doc_guidelines' not found` entry both said otherwise.

* **Stopped the evaluator failing on documents it cannot score.** Files with no evaluable content after frontmatter and MDX stripping&mdash;spec-driven pages that are only frontmatter and component references&mdash;are skipped with a reason instead of failing with `Error code 400: user messages must have non-empty content` after a wasted API call.

* **Corrected the `RAG-enhanced` pipeline diagram.** It showed guideline retrieval before the file was read, which is impossible since the retrieval query is built from the document's opening content. It also labeled two boxes `evaluate.py` inside the RAG lanes, wrote `evaluate-rag.py` with a hyphen, and ended on "JSON response returned", which stopped being true when that path moved to structured tool output in July.

* **Resolved contradictory workflow guidance.** [Supported formats](docs/supported-formats.md) instructed readers to copy files into `samples/` while [Batch evaluation](docs/batch-evaluation.md) told them to point at any folder. Files are read wherever they live.

* **Fixed stale self-references left by the README split.** Five passages across three pages still said "this README" while sitting in `docs/`, referring to a Customization section that had become its own page.

* **Hardened `tools/check_docs.py` against false positives found by running it against real documentation sets.** Each was surfaced by use rather than by review.
    * It read `.md` only, so a run against a Mintlify repository checked the meta files and none of the published `.mdx` pages. It now reads `.md`, `.mdx`, `.yaml`, and `.yml`, with the dash rule staying Markdown-only because specifications are also consumed by tools that render an entity literally.
    * Site-absolute links such as `/reference/authentication` were reported as broken; they are routes resolved by the documentation platform, not paths on disk. Extensionless links now resolve the way a site generator resolves them.
    * Code spans were replaced with an empty string, joining the words on either side, so ``such as `x` as shown`` collapsed to `such as as shown` and reported a repeated word. Link checking read the raw file, so an example link written inside backticks was resolved against the filesystem.
    * Headings containing an HTML entity produced a different anchor from headings containing the literal character, so converting a dash in a heading would have reported every working link to it as broken.

* **Rewrote the `.codespellrc` skip patterns as path globs.** Relative forms such as `./node_modules` resolve against the working directory, so they silently matched nothing when codespell was pointed at another repository, which returned thousands of misspellings from vendored packages. Documented targeting a documentation folder rather than a repository root, and how to check a run's scope before scanning an unfamiliar tree.

## July 2026

* Improved the CI runner's console output: an aligned, fixed-width score table (instead of raw Markdown pipes), with per-criterion feedback shown under it. By default, feedback appears only for docs that fail the gate; `-v`/`--verbose` shows it for every doc and `-q`/`--quiet` shows only the table. Console formatting is independent of the Markdown report used for the PR comment. Also recovers gracefully when the model misfiles a feedback sentence into a score field.
* Flattened the evaluation tool schema to top-level scalar fields (`clarity_score`, `clarity_feedback`, … `overall_score`, `overall_summary`) instead of nested `{score, feedback}` objects. Haiku reliably fills flat integer/string fields but frequently mangled the nested inner fields (leaking tool-call syntax into values), producing false failures on the majority of docs in a batch run. `score_document` reassembles the flat fields into the nested shape the rest of the code uses, so callers are unaffected.
* Hardened the CI report renderer against malformed model output. Although the evaluator requests a structured `{score, feedback}` object per criterion, the model can occasionally return a bare string or number; the renderer now tolerates that (showing `?` for a missing score and keeping any stray text as feedback) instead of crashing the run. A malformed `overall` safely gates to a failure rather than passing silently.
* Added a `skip-evaluation: true` frontmatter flag so non-API docs (portfolio overviews, process memos, changelogs) can opt out of scoring. The CI runner skips flagged files&mdash;they aren't scored, don't count toward the gate, and are noted in the PR comment. Prevents false failures from judging non-API pages against the API-reference rubric.
* Switched the RAG evaluator to structured tool-use output. `evaluate_rag.py`, `evaluate_core.py`, and the CI runner now receive the evaluation as a forced `submit_evaluation` tool call, so the SDK returns an already-parsed object instead of JSON embedded in text. This eliminates the nondeterministic `JSON parse error` failures caused by unescaped double quotes inside feedback strings (e.g., a doc scoring 4.6 that errored on a `("winner")` quote). No new dependency required.
* Added continuous integration via a GitHub Action (`.github/workflows/doc-quality.yml` and `ci/evaluate_changed.py`). OFor each pull request, it scores the changed documentation files, posts a sticky comment with a per-file score table and per-criterion feedback, and fails the check if any doc scores below the configurable `DOC_QUALITY_THRESHOLD` (default `3`). See [Continuous integration](docs/continuous-integration.md).
* Extracted the shared evaluation logic into `evaluate_core.py`, imported by both `evaluate_rag.py` (CLI) and the CI runner, so the two share a single source of truth. `evaluate_rag.py` is now a thin command-line wrapper that retains the same behavior and output.
* Fixed `requirements.txt`, which was missing `chromadb` and `python-frontmatter` (both imported by the evaluator).
* Added the `RAG-enhanced` evaluation feature (`evaluate_rag.py`, `build_index.py`, and the `knowledge_base/` folder).
* Added `docType` frontmatter support to `evaluate_rag.py`. The declared type is read and passed into the evaluation prompt, so the Structure and Completeness criteria are graded against that type's own checklist instead of an inferred one.
* Added `overview` as a fifth, practical (non-canonical) Diátaxis type in `diataxis_types.md`, for navigational index and hub pages.
* Added `integration-guide` as a sixth `docType`&mdash;a how-to specialization for implementation walkthroughs, scored structurally as `how-to` but additionally grounding Completeness against the Integration Guide Standards in `api_doc_standards.md`. Tagged that section in `DOCTYPE_HEADERS` for guaranteed retrieval.
* Added guaranteed retrieval to `build_index.py` and `evaluate_rag.py`: the declared `docType`'s own guideline chunk is always included in retrieval via metadata filtering, regardless of similarity ranking.
* Re-ran both evaluators against the current README and updated `sample_comparison_report.txt` with the new results, including a confirmed factual-error finding now folded into Known limitations. Clarified that the report's `knowledge_base` and `retrieved_chunks` fields are compiled from console retrieval diagnostics, not part of the evaluator's own JSON schema. Converted the README-related sample outputs to `.txt` in `txt_samples/` to capture full console output.
* Added support for the MDX format. MDX-specific syntax (frontmatter, imports, JSX tags) is stripped before evaluation; content inside JSX components is preserved.
* Changed how you specify the file to evaluate. The previous setup instructions said to add your file to the `samples/` folder, update `DOC_PATH` in `evaluate.py`, and run the `python3 evaluate.py` command in the terminal. Both scripts now require the file path as a command-line argument, for example:

    ```text
    python3 evaluate.py samples/my-doc.mdx
    python3 evaluate_rag.py samples/my-doc.mdx
    ```

* Increased `max_tokens` from 1024 to 2048 in `evaluate_rag.py` to prevent truncated responses on longer documents.
* Added JSON parse error handling. If the model's response can't be parsed, the evaluator now prints the parse error and the raw response for debugging instead of an unhandled traceback.
* Ported JSON parse error handling from `evaluate_rag.py` to `evaluate.py`, so both scripts print the parse error and raw response instead of an unhandled traceback.
* Added run-to-run variance guidance based on a second evaluation of this README; updated the comparison report's version note accordingly.

## May 2026

* **Fix (consistency criterion)**: The evaluator incorrectly flagged camelCase JSON field names (e.g., `bookId`) and snake_case Python variable names (e.g., `book_id`) as inconsistent. These reflect correct language conventions. The consistency prompt now distinguishes cross-language naming differences (not a flag) from genuine inconsistencies such as mixed conventions within a single language or mismatched field names passed between languages.
